# Независимый резерв на Яндекс Диске

Этот модуль сохраняет семь рабочих файлов бота в отдельном шифрованном
репозитории `PsychologiaPRO_backups/restic-v1` на платном Яндекс Диске.
Для шифрования, сжатия и повторного использования неизменившихся блоков
используются restic 0.19.1 и rclone 1.75.2. Секреты, исходный код, исполняемые
файлы, кэш и служебные каталоги в набор данных не входят.

## Состав и согласованность

В набор входят `memory.db`, `private_history.jsonl`, `private_dialog_state.json`,
`messages.jsonl`, `messages.txt`, `topics.json`, `diagnostics.jsonl`.
Манифест содержит время, размеры и SHA-256 всех семи компонентов.

Работающий бот удерживает существующую аренду каталога данных.
Снимок создаётся под `dialog_lock`, который используют также обработчики
групповых сообщений и названий тем. SQLite копируется через backup API,
включая зафиксированные изменения WAL. Частный архив и диагностика защищены
стабильными файловыми блокировками. Передача в облако выполняется после
освобождения `dialog_lock`; незашифрованный временный набор удаляется после
успеха или ошибки. Отмена задачи дожидается завершения файловой операции.

Файлы проверяются потоково, SQLite проходит проверку целостности, структуры,
владения и сроков источников. Источники частных сообщений старше 365 суток
удаляются только из копии. Исходные даты и рабочие файлы при этом сохраняются.

## Подготовка и первый запуск

Перенос кода в `main`, обновление документов и приёмка на Bothost выполняются
по регламенту проекта. Подготовка кода и тесты не подтверждают запуск резерва
на рабочем сервере.

В переменных Bothost необходимы:

| Переменная | Значение |
| --- | --- |
| `YANDEX_DISK_LOGIN` | Логин владельца Диска |
| `YANDEX_DISK_APP_PASSWORD` | Пароль приложения «Файлы / WebDAV» |
| `BACKUP_ENCRYPTION_KEY` | 64 шестнадцатеричных символа, созданные `secrets.token_hex(32)` |

Ключ сохраняется владельцем отдельно от Bothost. Его потеря делает архив
невосстановимым. Его нельзя отправлять в Telegram, чат разработки, GitHub
или документы. Переменные передаются дочерним программам через ограниченное
окружение, без токена Telegram и ключей ИИ. В аргументах команд их нет.

После согласованной установки кода и пересборки установить программы одной
обычной командой в терминале Bothost:

```text
python3 /app/tools/install_backup_tools.py
```

Установщик поддерживает Linux amd64/arm64, получает официальные архивы
GitHub, проверяет закреплённые SHA-256 и сохраняет программы в
`/app/data/.backup-tools`. Ранее проверенная установка используется повторно.
При ошибке копирование не объявляется успешным.

Затем владелец отправляет боту в личном чате:

```text
/backup_now
```

Первый запуск проверяет квоту и доступ, создаёт репозиторий только при
подтверждённом HTTP 404 его конфигурации, шифрует и сохраняет снимок,
считывает метаданные обратно и восстанавливает все семь файлов в новый
изолированный каталог. Ошибки авторизации, сервера или неверный ключ не
разрешают пересоздать существующий репозиторий. По умолчанию требуется
не менее 5 ГиБ свободного места в облаке.

Результат доступен владельцу через `/diagnostics 1`: число файлов, размер,
добавленные в резерв байты, свободное место, краткий идентификатор снимка,
проверка восстановления и класс ошибки без её содержимого. Команда
`/backup_now` недоступна другим пользователям и в группах.

## Автоматический режим и версии

Автоматический режим выключен до явной настройки `BACKUP_ENABLED=1`.
Его включают после успешной приёмки ручного копирования на Bothost.
После запуска бота выполняется первый проход и затем один проход в час.
Параллельные проходы внутри процесса исключены. Пропущенные интервалы
не запускаются очередью. Сбой не останавливает бота; следующая попытка
выполняется на следующем интервале.

Каждый проход создаёт полный логический снимок, а restic передаёт новые
блоки. Повторное скачивание полного архива выполняется при первом успешном
проходе и при ручном `/backup_now`; обычные проходы проверяют считывание
аутентифицированных метаданных. Это не заменяет периодическую контрольную
проверку восстановления владельцем.

| Необязательная переменная | По умолчанию | Ограничение |
| --- | --- | --- |
| `BACKUP_INTERVAL_SECONDS` | `3600` | 60–86400 секунд |
| `BACKUP_MIN_FREE_BYTES` | `5368709120` | Неотрицательное число байт |
| `BACKUP_TOOLS_DIR` | `/app/data/.backup-tools` | Каталог программ |
| `BACKUP_PRUNE_ENABLED` | `0` | `0` или `1` |
| `BACKUP_KEEP_DAYS` | `30` | 1–90 суток; действует при включённой очистке |

Удаление старых версий по умолчанию выключено. Значение 30 суток —
подготовленный вариант настройки, а не согласованное разрешение на удаление.
Включение очистки требует отдельного решения владельца. После включения
`BACKUP_PRUNE_ENABLED=1` не чаще раза в сутки, только после успешного
сохранения и имеющейся проверки восстановления выполняются `check` и
`forget --keep-within ... --prune` для выделенных host/tag этого репозитория.
Прочие файлы Диска и прежний резерв Google Drive не затрагиваются.
Без очистки история снимков растёт и может заполнить облако.

## Изолированное восстановление

Полный идентификатор снимка хранится в служебном
`/app/data/.backup-work/state.json`. Файл не содержит ключей или переписки.
Пример команды, в которой идентификатор нужно заменить фактическим:

```text
python3 -m memory.backup FULL_SNAPSHOT_ID --destination /app/restore_review_20261105
```

Целевой каталог должен быть новым и находиться вне рабочего каталога данных.
Восстановление проверяет манифест и семь файлов, повторно применяет 365 суток
по исходным датам на момент восстановления и обязательно создаёт
`recovery_review_required.json`. Архивный манифест относится к данным до этой
повторной очистки. Флаг восстановления автоматически не удаляется.
Команда не включает восстановленную копию в работу.

Перед активацией необходимо по регламенту сверить последующие удаления,
отзывы согласий, изменения памяти и сессий. Старый снимок сам по себе
не подтверждает актуальность этих действий. Рабочий бот не запускается
поверх набора с флагом проверки восстановления.

## Ресурсы и границы приёмки

Перед снимком проверяется локальное место для полного временного набора,
WAL и запаса. На время получения и проверки снимка обработчики, использующие
`dialog_lock`, ожидают. Первый контрольный проход требует также места для
полного восстановления. Кэш restic и служебные программы занимают место
на Bothost; объём Яндекс Диска не увеличивает диск и производительность
сервера. Настройка не является подтверждением нагрузки 5000 активных
участников. Её проверяют отдельно по фактическому росту данных, времени
снимка, ресурсам сервера и ограничениям облака.

CI выполняет весь существующий набор тестов памяти и обязательные проверки
нативными программами: зашифрованное сохранение и восстановление,
дедупликацию, локальный WebDAV, неверный ключ, повреждённый блок,
изолированное восстановление, согласованность, отказы и выключенную
по умолчанию очистку. Это тестовые наборы без рабочих данных и секретов.
